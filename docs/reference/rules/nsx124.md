## What it checks

`nimblestax.platform.yaml` sets `catalog` and `schema` patterns that aren't a Naming Style, or sets any patterns at version 2 or later, which take only `naming.style`.

## Why

Each Naming Style is a layout Nimblestax tests end to end. A pattern of your own can go wrong in ways a style can't: dev and prod can write to one table, every Domain's silver can land in one schema, and two Domains joined with their Layers can give the same schema name. Nimblestax reads a version 1 file's patterns as the style they match, and has no way yet to check patterns that match none.

## Example

Write this file into the project `nsx init` creates, and `nsx validate` fails:

`nimblestax.platform.yaml`:

```yaml
kind: platform
version: 3
name: shop
environments:
  dev:
    host: https://your-workspace.cloud.databricks.com
    role: development
naming:
  catalog: "{env}"
  schema: "{layer}"
  layers:
    models: [gold]
domains:
  - sales
```

## Fix

Replace `catalog` and `schema` with `style`, set to `system-and-domain-catalogs`, `layer-catalogs` or `environment-catalogs`, and set `version: 3`. For a version 1 file, the diagnostic names the closest style. If the project is deployed, check where the style puts each table first, because a new style moves them. If none of the styles fits, see [When none of these fit](../../concepts/naming.md#when-none-of-these-fit).
